**VoteKick public/private protocol investigation — October 4, 2026**

The tested public room rejects a second client during application admission, after HTTP routing, WebSocket upgrade, Engine.IO opening and Socket.IO connection have all succeeded. A normal invitation, independent of the extension, receives `joinerr:100`. The same browser/network and the same server route admit a second client into a private room. Together with the existing helper code and historical admission tests, these findings indicate that the current same-environment VoteKick approach is blocked by public-room admission in the tested environment. There is no demonstrated client-only change that resolves that rejection. The server's duplicate-identity key remains unknown; calling it an IP restriction would overstate the evidence.

This is a conclusion about the observed build, server route and environment. Public invitations are supported by the native UI. The evidence does not establish that all public invitations, every server, or independently admitted clients are prohibited. It establishes that fresh transport sessions in this environment do not create identities the tested public admission policy accepts.

The extension's functional code was inspected and left unchanged. New work is confined to this artifact directory: current first-party source snapshots, fetch metadata/hashes, a bounded admission collector, an offline evidence verifier, this report, and supporting reviews.

**How the application is organized.** The observed architecture has a same-origin HTTP entry/routing endpoint and a separate game service speaking Socket.IO over Engine.IO. `/api/play` supplies a destination URL; it does not return a room list or an application authentication token in these responses. The native client moves the returned destination port into a transport path on the HTTPS host. In this run the service URL's `:5005` became `/5005/` over TLS, rather than a browser connection to TCP port 5005. The specific proxy topology, selection algorithm and backend process layout are server-side unknowns.

Public Play supplies the selected language and an empty join value. The server selects or allocates a public lobby and later supplies its identifier. A private creator uses the same lookup and transport protocol but sets the application creation flag. Invitations to both room types supply an already-known room identifier. The initial server snapshot establishes the actual mode: public `type:0`, private `type:1` in this experiment. A public room has an invitation identifier and is not anonymous at the protocol level. The native site explicitly presents public invitations as a feature. [Official site](https://skribbl.io/), [current client snapshot](game.js), [source anchors](protocol-source-evidence.json).

No additional distinct account ID, authentication session token, game-instance token or match ID was exposed in the inspected login/snapshot path. `round`/`state` are game state, not proof of a separate global match identifier. This does not exclude identifiers held only in backend or edge state.

Both newly observed room strings were eight alphanumeric characters and did not end in digits. Two samples cannot establish a predictable pattern, randomness, entropy, collision behavior or cryptographic generation. The client receives these values from the server; it does not generate them. No identifier enumeration or guessing was performed. The original public room's ID is already known to VoteKick from the primary snapshot, so predictable IDs would not address its current failure.

**Connection flow.** The native sequence observed in all four cases is:

1. Load the homepage/invitation page and first-party `js/socket.io.js` and `js/game.js`.
2. Click Play or Create Private Room. Native code may run its advertisement timing gate; this is separate from admission. It stores `lastAd` locally and normally continues immediately on first use.
3. Send same-origin `POST /api/play` with `application/x-www-form-urlencoded`. Public Play and private creation use `lang=<language>`; invitations use `id=<room>`. HTTP 200 response text gives the service URL.
4. Open the game WebSocket using the service host and port-derived path, query `EIO=4&transport=websocket`, normal browser Upgrade headers, and the Skribbl page Origin. The server returns HTTP 101.
5. Receive Engine.IO open `0{sid,...}`. In all four connections the server advertised 5,000 ms ping interval, 20,000 ms ping timeout and 81,920-byte max payload. These are transport heartbeat/payload settings, not measured join-rate limits.
6. Send Socket.IO namespace CONNECT `40`; receive `40{sid:<socket-id>}`. No namespace auth payload was observed. The current fetched distribution identifies Socket.IO 4.8.3, parser protocol 5 and Engine.IO protocol 4.
7. Emit `login`. Public matchmaking uses `join:"",create:0`; private creation uses numeric `join:0,create:1` (the source-confirmed canonical creation value; the original collector's numeric-alias defect is disclosed above); either invitation uses `join:<server-issued-room>,create:0`. All include ordinary name, language and avatar.
8. Receive application `data` packet 10 containing the admitted lobby snapshot, or `joinerr`. The public invited peer receives 100 here. It has already passed every preceding stage.
9. Maintain Engine.IO ping/pong while connected; close on completion/failure.

The native code lists WebSocket before polling. All four captured connections used WebSocket directly; no polling path was exercised. The current library does not guarantee trying polling after a failed opening transport unless its relevant retry option is enabled; the game does not set that option. A hypothetical raw WebSocket client would need the Engine.IO and Socket.IO layers, not only a successful HTTP upgrade. VoteKick uses the site's own library, so those layers are already supplied. [Engine.IO specification](https://socket.io/docs/v4/engine-io-protocol/), [Socket.IO specification](https://socket.io/docs/v4/socket-io-protocol/).

Captured public/private differences are the lookup body and invitation Referer, login join/creation fields, snapshot type/owner/player values, and application admission outcome. The service host/path, browser User-Agent/client hints, Origin, upgrade success, namespace connection format and heartbeat parameters were shared. Cookies appeared on HTTP lookup requests in both modes; their contents were not compared. The collector normalizes URLs, including trailing slashes, and retains selected headers rather than every header. No observed login has a CAPTCHA response, app token or fingerprint field. This describes the observed path; it does not prove absence of backend risk scoring, edge controls, or indirect cookie-derived server state.

**Existing VoteKick architecture and bottleneck.** [manifest.json](C:/Users/Noel/Documents/Skribbl-io/Skribbl-io-auto-drawer/manifest.json:15) loads the isolated UI at document idle and [the runner](C:/Users/Noel/Documents/Skribbl-io/Skribbl-io-auto-drawer/votekick-runner.js:403) in the page MAIN world at document start. The runner wraps the native `window.io` factory, observes native login, and learns the primary lobby, player IDs, owner, type and capacity from packet 10. [votekick.js](C:/Users/Noel/Documents/Skribbl-io/Skribbl-io-auto-drawer/votekick.js:35) passes snapshot/start/stop requests over DOM events. Helpers are additional socket sessions within that same page, not independent browser profiles or identities.

[Helper creation](C:/Users/Noel/Documents/Skribbl-io/Skribbl-io-auto-drawer/votekick-runner.js:460) reuses the primary factory, endpoint and transport path; sets `forceNew:true`, `multiplex:false`, `reconnection:false` and an 8-second timeout; omits optional primary auth/query; then logs in with the known room ID, `create:0`, helper name, primary language and copied avatar. It does not call `/api/play` itself. The fetched real Socket.IO library was also checked offline with `autoConnect:false`: these options create distinct socket objects and managers without network activity. [Verifier](verify-evidence.cjs), [Socket.IO options](https://socket.io/docs/v4/client-options/).

The primary casts its vote first. A helper votes only after its packet-10 snapshot verifies the exact room and a separate player ID. Helpers join sequentially, subject to open slots, with 1-second spacing after the first. Votes use numeric target player IDs, not room/connection IDs. The runner waits for server vote broadcasts and uses the returned vote count and required count. Removal is a separate server departure event; merely emitting a vote does not establish removal. Cleanup preserves the primary connection. [Vote lifecycle](C:/Users/Noel/Documents/Skribbl-io/Skribbl-io-auto-drawer/votekick-runner.js:576).

The specific failure is [helper application admission](C:/Users/Noel/Documents/Skribbl-io/Skribbl-io-auto-drawer/votekick-runner.js:523). `joinerr:100` prevents a packet-10 admission and therefore prevents that helper from becoming a voter. When its own helper receives public code 100, the runner caches that rejection for the primary lobby session and later uses only the primary vote, avoiding repeated refused connections. The fresh native admission-only probe did not execute that voting flow or populate its cache. [Existing fallback](C:/Users/Noel/Documents/Skribbl-io/Skribbl-io-auto-drawer/votekick-runner.js:592), [error handling](C:/Users/Noel/Documents/Skribbl-io/Skribbl-io-auto-drawer/votekick-runner.js:645). These protections are existing behavior, not proposed new changes.

Skipping lookup is a protocol difference worth documenting, but a normal native invitation performed the lookup and received the same rejection. Distinct avatars and names also failed in this fresh test. Therefore lookup omission, cosmetic identity and local Socket.IO reuse are not supported explanations of the demonstrated public failure. Creating another private room would not place clients in the selected public room. The shared route successfully admitting the private invitation makes a universal broken handshake or global two-connection transport cap inconsistent with this run.

The fresh experiment verified private admission of one extra native client. It did not execute the VoteKick run or verify private vote thresholds/removal live. Private VoteKick functionality is the user's report plus code compatibility and offline regression tests. That distinction matters: private admission does not prove unlimited helpers or guaranteed removal.

The most defensible root-cause statement is a public-mode admission restriction treating the second login as duplicate presence in the tested environment. Public/private admission divergence is observed; a causal room-mode branch, the particular policy key and the decision branch require owned server source/logs or additional controlled experiments. Public-first/private-second order, one route/language, headless browser characteristics, shared egress, and the small sample remain limitations. No backend source, configuration, admission logs, exact rate limits, fingerprint rules, quorum formula, vote expiry, or server vote deduplication implementation is available in this repository. No current load limit was measured.

**Proxies/VPNs and controlled concurrency.** A changed source address could alter admission only if the relevant rule uses that address or an address-derived identity. That would not establish a defect in room discovery or handshake. It could have no effect where the decision uses cookies or supported credentials, persistent server principal/session state, browser/process signals, shared behavior, or overlapping connection/timing patterns. A VPN may leave many clients sharing one egress address. Proxy reputation/edge classification could introduce a new confound. These are conceptual possibilities, not validated behavior; no proxy, VPN or fingerprint rotation was tested or implemented.

For a valid ownership test, use a staging deployment with production-equivalent public-mode admission code and known controlled clients. Provision explicit test identities or a gated test admission path, record the actual denial rule, and change one input at a time. A fixed set of owned test nodes with known egress addresses can measure network-scoped policy. Increase bounded concurrency according to a predeclared schedule, capture admission/latency/disconnect/limit counters, and stop at agreed limits. Public-mode rooms can run in staging with no public participants. Multi-client vote behavior should then target only designated test clients. This produces meaningful concurrency evidence without making production proxy rotation part of the solution.

**Viable changes and limitations.** No production VoteKick change is currently supported as a way to defeat code 100. The viable owner-side route is to establish the public admission identity rule and supply an explicit, gated way to admit controlled test principals where appropriate. If the rule intentionally maps all same-environment helpers to the already-admitted principal, client-created sockets alone cannot give them independent voting eligibility. The present approach is blocked by that admission decision in the tested public room. If server logs instead reveal a missing supported credential, route issuance step or parser incompatibility, correct that specific flow using separately issued client credentials and revalidate; do not assume such a defect exists.

Potential extension changes, after that decision, concern [helper admission](C:/Users/Noel/Documents/Skribbl-io/Skribbl-io-auto-drawer/votekick-runner.js:460), [primary login capture](C:/Users/Noel/Documents/Skribbl-io/Skribbl-io-auto-drawer/votekick-runner.js:326), [lobby snapshot validation](C:/Users/Noel/Documents/Skribbl-io/Skribbl-io-auto-drawer/votekick-runner.js:87), [rejection/fallback](C:/Users/Noel/Documents/Skribbl-io/Skribbl-io-auto-drawer/votekick-runner.js:448), and [UI admission diagnostics](C:/Users/Noel/Documents/Skribbl-io/Skribbl-io-auto-drawer/votekick.js:56). Add phase-specific diagnostics and a supported test endpoint/credential provider if the owned server exposes one. Use lookup per helper only if contract or routing can change; this experiment shows it is not by itself a remedy. Keep server-authoritative vote counts, protected-target checks, no retry on denial, and cleanup. One-second helper spacing is an implementation constant, not a proven permitted rate. Adding helpers can increase the server's required quorum, and admission never guarantees a kick.
